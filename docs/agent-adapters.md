# Agent adapters

An **Agent adapter** teaches the Orchestrator to launch, resume and observe one kind of Agent. Adapters are compiled in: the trait lives in `crates/orch-agent/src/agent.rs`, and there are two implementations: Claude Code (`crates/orch-agent/src/claude/`) and Antigravity (`crates/orch-agent/src/antigravity/`, the `agy` CLI). Antigravity launches, resumes, drafts, reports Agent states and usage, tracks modes, shows Subagents with their transcripts, answers Guards and enforces its Preset rules.

The Agent's own TUI always runs in the Holder's PTY (ADR 0001). The adapter never renders anything. It only builds command lines and translates the Agent's side-channel output (hooks, statusline, and files the Agent writes such as its transcript) into the normalized event vocabulary. The Daemon's status machine depends on nothing else.

## The trait

```rust
pub trait AgentAdapter {
    fn capabilities(&self) -> Capabilities;
    fn launch(&self, spec: &LaunchSpec) -> Argv;
    fn modes(&self) -> &'static [PermissionMode];
    fn resume(&self, spec: &LaunchSpec, conversation: &ConversationId, mode: Option<PermissionMode>) -> Option<Argv>;
    fn restart(&self, spec: &LaunchSpec, conversation: Option<&ConversationId>, mode: Option<PermissionMode>) -> Argv;
    fn draft(&self, conversation: Option<&ConversationId>) -> Option<Draft>;
    fn encode_draft(&self, prompt: &str) -> String;
    fn decode_draft(&self, stdout: &str) -> DraftOutcome;
    fn map_hook(&self, payload: &str) -> Result<Vec<AgentEvent>, PayloadError>;
    fn map_tap(&self, payload: &str) -> Result<Vec<AgentEvent>, PayloadError>;
    fn title_watch(&self) -> Option<Box<dyn TitleWatch>>;
    fn subagent_transcripts(&self) -> Option<Box<dyn SubagentTranscripts>>;
    fn conversation_tree(&self) -> Option<Box<dyn ConversationTree>>;
    fn is_guard_payload(&self, payload: &str) -> bool;
    fn guard_answer(&self, answer: &GuardAnswer) -> Option<String>;
    fn enforces_rules(&self) -> bool;
    fn rule_verdict(&self, preset: &Preset, action: &GuardedAction, scope: &RuleScope) -> Option<RuleVerdict>;
    fn fallback_hook_reply(&self) -> Option<String>;
    fn fallback_statusline(&self, payload: &str) -> String;
    fn hookup(&self) -> Option<Box<dyn AgentHookup>>;
    fn agent_dirs(&self, lookup: &dyn Fn(&str) -> Option<String>) -> Vec<PathBuf>;
    fn user_statusline_command(&self, cwd: &Path, lookup: &dyn Fn(&str) -> Option<String>) -> Option<String>;
}
```

Only `capabilities` and `launch` are required. Every other method has a default that matches "capability absent".

A Draft is the `Draft` struct (`argv` plus `input`) together with the adapter's `encode_draft` and `decode_draft`.

| Method | Supplies |
|---|---|
| `launch` | The argv that starts a fresh Agent in the Worktree. `LaunchSpec` carries the Session id, the absolute `orch` binary (for hook and tap commands), the effective Preset and an optional initial prompt. Claude gets `--session-id`, `--settings` JSON (hooks → `orch hook --agent claude --session <id>`, `statusLine` → `orch tap --agent claude --session <id>`, the Preset's allow/deny), and `--permission-mode` unless the Preset is `inherit`. Antigravity takes its hooks and statusline from its Agent hookup instead, so it only gets `--mode accept-edits` or `--mode plan` (none for `default` and `inherit`) and `-i <prompt>`. |
| `modes` | The Preset modes the Agent can express, from the shared vocabulary (`default`, `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions`; `inherit` always works). The `:new` form only offers Presets with one of these modes, `:new` and `:preset` refuse any other, and a Repo or global default Preset outside them falls back to `edits` (or `inherit`, if `edits` is outside them too). The default is none, so only `inherit` and mode-less Presets. Claude supports all of them, Antigravity `default`, `acceptEdits` and `plan`. An adapter reads only its own rules, `Preset::rules_for(<its Agent name>)`; in config, Claude's are the top-level `allow`/`deny` of `[presets.<name>]` and other Agents' are in `[presets.<name>.<agent>]` (names from `orch_agent::built_in_names`). |
| `resume` | The argv that continues the latest Conversation in the last observed mode. `None` means the Agent can't resume, so `restart` falls back to `launch`. Claude uses `--resume <conv>`, Antigravity `--conversation <conv>`; both add the mode flag of the last observed mode (the Preset's before any was observed), and none for an `inherit` Preset. |
| `draft` | A side-channel one-shot that drafts a commit message or PR title/body without adding turns to the live Conversation (ADR 0007), given the latest Conversation if there is one. The Daemon runs `Draft.argv` in the Worktree without `ORCH_SESSION`, pipes the Draft prompt, framed by `encode_draft`, into its stdin and closes it, then reads stdout with `decode_draft` as a `DraftOutcome`: `Drafted(text)`, `NoResult` or `Failed(error)`. The defaults pipe the prompt as is and take stdout as the draft. Antigravity sends one NDJSON line `{"event":"user","message":{"content":[{"type":"text","text":<prompt>}]}}` and reads the draft from the `response` of the last `{"event":"result","result":{…}}` event on stdout; a `SUCCESS` result with a missing, non-string or blank `response` fails with "agy returned an empty response". `Failed` refuses the Draft with the Agent's error (agy's `error` for a result whose `status` isn't `SUCCESS`), whatever the exit code; no result refuses it too (with stderr if the Agent failed). When `Draft.input` is `InstructionAndBaseDiff`, the Daemon appends the diff against the Base branch (from the merge base, including uncommitted and untracked files), for an Agent that can't see the Conversation: a `--stat` of every changed file, then the patch, cut at a line boundary after 100 KiB with a marker. `None` means the Agent can't draft, and the Draft falls back to the Session's prompt; so does a Session without a Conversation whose Agent config or binary can't be loaded. Claude uses `-p --resume <conv> --fork-session` with the instruction alone, and can't draft before it has a Conversation. Antigravity can't fork a Conversation (`--conversation` appends to it), so it runs a fresh `agy -p '' --input-format stream-json --output-format stream-json` (agy's `-p` needs an argument; the empty one leaves the prompt to stdin) with the instruction and the Base diff, framed as stream-json. |
| `map_hook` | Parses one hook payload, which `orch hook` forwards through the Holder, into normalized events. Every hook and statusline command an adapter injects carries `--agent <name>`: `orch hook` and `orch tap` pick the adapter from that flag (`orch_agent::by_name`) without asking the Daemon, and the Daemon drops payloads whose Agent isn't the Session's (ADR 0006). `--agent` defaults to `claude`, because Sessions started before the flag existed run hook and statusline commands without it. An Agent whose payloads don't name their hook event gets `--event <name>` in each hook command, and `orch hook` adds it to the payload as `orch_hook_event` (`orch_agent::tag_hook_event`). Antigravity maps `PreInvocation` to `PromptSubmitted` (`PostInvocation` to nothing), `PreToolUse` to `ToolStarted` (or `QuestionAsked` for `ask_question`), `PostToolUse` to `ToolFinished`, a `Stop` with `fullyIdle: true` to `TurnEnded` (one with `fullyIdle: false` to nothing), and a `Stop` whose `terminationReason` is `error` or `max_steps_exceeded` (any case) to `Failed`. On its own it takes no Conversation from hooks, because a Subagent's hooks carry the Subagent's own id; its `conversation_tree` sorts that out. |
| `map_tap` | Parses one statusline payload, which `orch tap` forwards, into normalized events. Claude's become `UsageSample`s. Antigravity's statusline is its only Needs input and mode signal: `conversation_id` gives `ConversationChanged`, `cycle_mode` gives `ModeChanged` (absent means `default`; not reported while `agent_state` is `authenticating` or `initializing`), `tool_confirmation_pending: true` gives `PermissionRequested`, any other line `PermissionCleared`, and an `idle` line that names a Conversation also `AwaitingPrompt`, since agy has no session-start hook. An `idle` line with an empty `conversation_id` is not readiness: agy has no Conversation yet. agy's workspace-trust screen gives no signal of its own: the statusline says `agent_state: "initializing"` (no `tool_confirmation_pending`, no hook) until the user answers it in the pane, which looks the same as a slow start, so an Antigravity Session shows the workspace-trust screen as Starting. Live checks against agy 1.3.1 found that this `initializing` line is all the screen shows, and that agy also reports `initializing` with no Conversation until its first turn, so a Session started without a prompt stays Starting until then. Every Antigravity line past start-up is also a `UsageSample`: model from `model.display_name`, context and tokens from `context_window`, no cost, and one usage window per `quota` pool (`gemini-weekly` as `gemini-wk`, `3p-weekly` as `3p-wk`, any other pool labelled by its name) with `used_percent` from `1 − remaining_fraction` and the reset from `reset_time`. agy omits a zero `remaining_fraction`, so a pool without one is fully used. |
| `title_watch` | A stateful `TitleWatch` that reports the Session title. The Daemon keeps one per Holder connection in its own task: it hands the watch every hook and statusline payload (`follow`, which only notes where to look) and calls `poll` right after each payload and about once a second, off the Daemon's state lock, so a title shows without waiting for the next hook. `poll` returns `TitleChanged` only when the title differs from the last one it reported. Claude follows `transcript_path`, reads the transcript incrementally and reports the last `custom-title` entry (`/rename`); the `session_title` field of SessionStart/UserPromptSubmit hooks only fills in while the transcript has no `custom-title` entry, and is forgotten when the transcript changes (a new Conversation). |
| `subagent_transcripts` | A stateful `SubagentTranscripts` per Session that finds each Subagent's transcript file. The Daemon hands it every hook payload (`follow`) and asks it for a Subagent's file (`locate`) and for a `TranscriptReader` per subscribing Client. `read` returns the entries added since the last read, and `reset` when it started over because the file changed or shrank. Claude derives `<transcript dir>/<conversation>/subagents/agent-<id>.jsonl` from the `transcript_path` of the Subagent's first hook (so it survives a new Conversation) and switches to `agent_transcript_path` once `SubagentStop` names it. It drops thinking, and a tool call's key argument is the first of `command`, `file_path`, `notebook_path`, `pattern`, `url`, `query`, `skill`, `description`, `prompt` in its input. Antigravity follows the `transcriptPath` of each Conversation's hooks (a `transcript.jsonl` there means its sibling `transcript_full.jsonl`) and reads agy's `transcript_full.jsonl` steps: `USER_INPUT` is a Prompt without its `<USER_REQUEST>` wrapper, a `[Message]` in a `SYSTEM_MESSAGE` from anyone but `system` is a Prompt (other notices are dropped), `PLANNER_RESPONSE` is Text plus a ToolCall per `tool_calls` entry (key argument the first of `CommandLine`, `TargetFile`, `AbsolutePath`, `Prompt`, `Message`, `Query`, `Url`, `DirectoryPath`, `SearchPath`, `Question`), and each following `GENERIC` step that opens with agy's `Created At:` stamp is the result of the oldest unanswered call (`status: ERROR` is an error). A step without `step_index` still gets call ids of its own. Thinking is dropped. |
| `conversation_tree` | A stateful `ConversationTree` per Session for an Agent whose hooks need context to attribute. When it exists, the Daemon maps hooks (`hook`) and statusline payloads (`tap`) through it instead of `map_hook`/`map_tap`, and calls `restart` with the Session's latest Conversation when the Session is loaded and with none whenever the Agent is spawned (not when a running Agent is adopted). Antigravity's Session Conversation is the statusline's `conversation_id`, or else the first hook's `conversationId` after a restart (reported as `ConversationChanged`) unless it is a known Subagent's. A hook from any other Conversation is a Subagent, nested ones included: its first hook gives `SubagentStarted` (its `PreInvocation` gives no `PromptSubmitted`, so it never reopens the Session's turn), its tools carry `subagent`, its `Stop` gives `SubagentFinished` (plus `TurnEnded` when `fullyIdle`, never `Failed`), and a later hook reopens the row. Its label comes from the pending `invoke_subagent` spec (`Subagents[]` of a `PreToolUse`) whose `Prompt` is the Subagent's first prompt in its transcript (`agent_type = TypeName`, `description = Role`); without a match it is type `subagent` with the prompt's first line. A matched spec is used up. While a row has that fallback label, each later hook retries the match (the transcript may not exist yet at the first hook) and sends `SubagentStarted` again with the new label, which relabels the row. |
| `is_guard_payload` / `guard_answer` | Marks the hook payloads that block until the Daemon answers a Guard, and renders the answer in the Agent's hook-output format. `GuardAnswer` is `Proceed` (no objection), `PresetAllow` (a Preset allow rule matched), `Ask` (orch couldn't decide, so the Agent must ask the user) or `Deny { reason }`. Claude prints nothing for `Proceed` and `PresetAllow`, since it enforces its own rules from `--settings`. Antigravity's `PreToolUse` always gets an explicit decision, because agy denies a reply without one: `Proceed` is `{"decision":"ask"}` (agy's own policy decides), `PresetAllow` is `allow`, `Ask` is `force_ask` and `Deny` is `deny` with `reason`. |
| `enforces_rules` / `rule_verdict` | For an Agent whose Preset rules can't travel per launch (`enforces_rules` is true): the Session's Preset's verdict on one guarded action, given a `RuleScope` (the call's cwd, the Worktree and an env lookup). `RuleVerdict::Deny { rule }` if any deny rule matches, else `Allow { rule }` if the allow rules cover the action, else `None`. The defaults are `false` and `None`, so Claude's rules stay with Claude. The Daemon combines the verdict with the Guard (`orch_agent::guard_outcome`) in the order Guard → Preset deny → Preset allow → ask. A Preset deny denies at once, **without a Guard prompt**, since the answer would be deny whatever the user chose. A Guard hit asks the user in orch and, once allowed, answers with the Preset allow (`GuardAnswer::PresetAllow`) or `Proceed`; otherwise that answer goes out straight away. So `allow` is only ever sent because the user wrote an allow rule. A guarded tool whose target the adapter can't read is `GuardedAction::Unreadable`: no rule matches it, and it is answered with `Ask` (agy's `force_ask`) while Guards are on; while they are off, the adapter's verdict is `RuleVerdict::Unverifiable` (also `Ask`) if the Preset has deny rules, and otherwise it gets `Proceed` (agy's own policy, `ask`). The Guard treats a redirect into a word the shell would expand (braces, globs, `~user`, `$`, …), or a relative one after a `cd` it can't follow, as WriteOutsideWorktree, and judges every redirect from each directory the command line has been in. The Daemon keeps the Preset each Session was launched with and re-reads it from config for Sessions it adopts after a restart; while it has none for an Agent that enforces rules, every guarded call is answered with `Ask` (`force_ask`), Guards on or off, because the user's deny rules can't be checked. The MCP config is read from the Daemon's `HOME`, which is the Session's too unless the Agent's launch changes it. Antigravity reads `Preset::rules_for("antigravity")` in agy's syntax; what each rule form matches, and why `allow` is strict while `deny` is best-effort, is described once in the [README](../README.md#configuration). |
| `agent_dirs` | Directories outside the Worktree where the Agent keeps its own per-Conversation files; the WriteOutsideWorktree Guard lets the Agent write there. Claude: `<config dir>/projects` and `<config dir>/plans`. Antigravity: `$HOME/.gemini/antigravity-cli/brain`. |
| `fallback_hook_reply` | What `orch hook` prints when it can't read or parse the payload, or has no Guard answer to print. It also prints it, besides reporting the hook, for a payload without `--event` that carries a `toolCall` but isn't a Guard payload, so an untagged tool call never gets silence. Antigravity treats a silent `PreToolUse` hook as a denial, so it replies `{"decision":"ask"}`. Claude needs none. |
| `fallback_statusline` | What `orch tap` prints when the user has no statusline command of their own. The default is a minimal model and context line; Antigravity prints nothing so agy's own line shows. |
| `hookup` | The Agent hookup (ADR 0005), for an Agent that can't take orch's hooks and statusline per launch. `AgentHookup` plans the file edits for `install` and `uninstall` (`orch agent install|uninstall <agent>` shows them as a diff before applying them) and reports its `state`: Missing, Installed or Broken. The Daemon refuses to create a Session of that Agent unless it is Installed, and `orch doctor` reports a Broken one. Its global hook and tap commands carry `--agent` but no `--session` (Antigravity's hook commands also carry `--event`), so `orch hook` and `orch tap` take the Session from `ORCH_SESSION`; without it the hook answers a Guard payload with `GuardAnswer::Proceed` and reports nothing, and the tap runs only the user's statusline command and prints nothing when there is none. Antigravity edits `~/.gemini/config/hooks.json` and `~/.gemini/antigravity-cli/settings.json`, and saves the user's previous statusline in `orch`'s state (`$XDG_STATE_HOME/orchestrator/hookups/antigravity.json`), where `user_statusline_command` reads it. That record also keeps each file's original bytes, written before agy's files, so uninstall restores a file exactly while it still holds what orch wrote, and otherwise removes only orch's parts. `apply` refuses a file that changed since the diff was shown, and install refuses a `"orch"` hook that orch did not write. An orch hook whose commands lack `--event` (installed before the tags) is Broken until a reinstall replaces it. |
| `user_statusline_command` | The user's own statusline command, which `orch tap` runs and prints in place of a minimal line. Claude reads it from managed, project-local, project and user settings in that order. |

## Capabilities and graceful degrade

`Capabilities { hooks, resume, usage, modes, guards, subagents, titles, transcripts }` declares what the Agent can do. Sessions of an Agent that lacks a capability still work, with less information:

| Missing | Behaviour |
|---|---|
| `hooks` | The Session uses the unobserved status machine, so its Agent state is **Unknown** ("activity unknown"). Exited and Errored still come from the process exit. There are no Guards, because Guards arrive as hooks. |
| `resume` | `resume` returns `None`, so resume, reboot recovery and `:preset` start a fresh Conversation. |
| `usage` | The adapter emits no `UsageSample`, so there is no context gauge, token totals or usage windows. |
| `modes` | The Daemon launches and resumes the Agent with the `inherit` Preset whatever was chosen (`Capabilities::effective_preset`, applied in `agent_command`), and no `ModeChanged` is reported. |
| `guards` | The Daemon lets every blocking hook proceed without evaluating it (`Capabilities::guards_available`, which needs both hooks and guards, gates the Guard path). |
| `subagents` | No `SubagentStarted`/`SubagentFinished`, so no nested Subagent rows. |
| `titles` | `title_watch` returns `None` and no `TitleChanged` is reported, so the Session keeps showing its slug. |
| `transcripts` | `subagent_transcripts` returns `None`, so subscribing to a Subagent is refused and there is no Subagent transcript (ADR 0004). |

## Normalized event vocabulary

The events come from `orch_core::AgentEvent`:

- `SessionStarted`, `PromptSubmitted`, `TurnEnded`
- `AwaitingPrompt`, for an Agent without a session-start hook: it shows it waits for a prompt. It makes the Agent Idle only until the Agent's first turn since it was spawned (a prompt, tool, question, turn end or failure), and does nothing after that, so a stale or repeated signal can't end a turn.
- `ToolStarted { tool, subagent }`, `ToolFinished { tool, subagent }`
- `PermissionRequested`, `PermissionDenied`, `QuestionAsked`
- `PermissionCleared`: the side channel shows no permission prompt any more. It leaves a Needs input that `PermissionRequested` set, back to Working, and leaves a question, a Guard prompt and every other state alone, so a side channel that lags behind the hooks never overrides what a hook set.
- `Failed { kind }`
- `ModeChanged { mode }`, `ConversationChanged { id }`
- `TitleChanged { title }`, the Session title the user gave through the Agent; an empty title clears it and brings the slug back
- `UsageSample { … }`. Its `windows` are named usage windows (`UsageWindow { name, label, used_percent, resets_at_unix }`); the adapter picks the short `label` the statusline shows, and Claude reports `5h` and `7d`. The Daemon keeps the latest value per (Agent, window), and the statusline leaves out a window once its `resets_at_unix` has passed. `cost_usd` stays `None` when the Agent doesn't report cost, and orch never estimates it; a total that includes any unknown cost is unknown too.
- `SubagentStarted { id, agent_type, description }`, `SubagentFinished { id }`
- `GuardCheck { tool, action, cwd }`, which the Daemon answers with allow, deny or ask. `action` is an Agent-neutral `GuardedAction`, and `tool` is only shown in the Guard prompt:
  - `WriteFile { path }`, a tool that writes or deletes a file; the path may be relative to `cwd`
  - `Shell { command }`, a shell command line
  - `ExternalTool { name }`, a tool that reaches beyond the Session (MCP, browser); the first use asks, and "allow for Session" covers that tool name afterwards

  The adapter emits `GuardCheck` only for tools it maps to an action, so `evaluate_guard` knows no tool names. Claude maps `Write`, `Edit` and `MultiEdit` (`file_path`) and `NotebookEdit` (`notebook_path`) to `WriteFile`, `Bash` (`command`) to `Shell`, and every `mcp__*` tool to `ExternalTool`. Antigravity maps `write_to_file`, `write_file`, `create_file`, `edit_file`, `replace_file_content`, `multi_replace_file_content`, `delete_file` and `edit_notebook` to `WriteFile` (the first of `TargetFile`, `AbsolutePath`, `FilePath`, `File` and `NotebookPath` in `toolCall.args`), `run_command` (`CommandLine`, cwd from `Cwd`) and `send_command_input` (`Input`) to `Shell`, and every `mcp_*` tool and every tool with a `browser` part in its name (`open_browser_url`, `browser_subagent`, …) to `ExternalTool`.

A Subagent transcript is a list of `orch_core::TranscriptEntry`, which the Daemon streams to subscribed Clients as is:

- `Prompt { text }`, what the Subagent was asked
- `Text { text }`, what it said
- `ToolCall { id, tool, argument }`, a tool it called and that call's key argument, if any
- `ToolResult { id, text, error }`, the full result of the call with the same `id`, and whether it failed

The mapping from these events to Agent states (Starting, Working, Needs input, Idle, Errored, Exited) is fixed in `orch-core` and is the same for every Agent. A restarted or resumed Agent finishes every open Subagent row, because its Subagents stopped with the old process. `orch-core` also gates a few events by the turn (`TurnGate`), so a side channel that lags behind the hooks never overrides what a hook set: `AwaitingPrompt` counts only before the first turn activity (`AgentEvent::is_turn_activity`), `PermissionRequested` is ignored after `TurnEnded` or `Failed` until the next `PromptSubmitted`, and `ToolStarted` is ignored while a `PermissionRequested` prompt is open, so an unattributed Subagent tool can't clear it.

## Checklist: adding an Agent (e.g. Codex CLI)

1. **Research the Agent.** Find out how it starts with a given id and initial prompt, how it resumes, which modes it has, whether it offers hooks or a statusline-like side channel, and whether it supports a non-interactive one-shot for drafting.
2. **Record fixtures.** Capture real hook and side-channel payloads into `crates/orch-agent/tests/fixtures/<agent>/`, and note the Agent version you recorded them with.
3. **Implement `AgentAdapter`** in `crates/orch-agent/src/<agent>/`:
   - declare `Capabilities` honestly, since a missing capability is fine and degrades as described above;
   - write `launch`, and `resume` / `draft` if the Agent supports them;
   - write `map_hook` / `map_tap` into the vocabulary above, and map anything that doesn't fit to nothing rather than inventing events;
   - if the Agent lets the user name a Conversation, implement `title_watch`; keep file reads there, so `map_hook` / `map_tap` stay pure;
   - if the Agent writes its Subagents' transcripts to files, implement `subagent_transcripts` into the entries above;
   - if a hook needs earlier hooks to be attributed (a Subagent's hooks that look like the Session's), implement `conversation_tree` around `map_hook` / `map_tap`;
   - for Guards, map each file-write, shell and external tool to a `GuardedAction` in `map_hook`, and implement `is_guard_payload` and `guard_answer` for the Agent's blocking-hook protocol.
4. **Inject per launch where the Agent allows it, otherwise through an Agent hookup (ADR 0005).** Per launch means flags or env, as the Claude adapter does with `--settings`, and never writing to the user's own Agent config. An Agent without that implements `hookup`, which only `orch agent install` writes, after showing the diff and asking.
5. **Test the mapping as pure functions** (Seam 3): fixture → events, and launch/resume argv for each Preset and capability combination. Test a `TitleWatch` through `follow` / `poll` and `SubagentTranscripts` through `follow` / `locate` / `read` against temporary transcript files. See `crates/orch-agent/tests/claude_*.rs`.
6. **Register the adapter** in `crates/orch-agent/src/built_in.rs` (`BUILT_IN`) under its config name, so that `agent = "<agent>"` or the `:new` form selects it, `[agents.<agent>]` configures its `binary` and `args`, and `orch hook` / `orch tap --agent <agent>` reach it.
7. **Run it end to end** with the scriptable fake Agent (`orch fake-agent`) through the Daemon tests, if the new adapter changes launch or event routing. The fake knows no Agent: configure it as `[agents.<agent>] binary` with `args = ["fake-agent", "--"]`; it echoes each `-flag value` of its argv as `flag> value`, replays `hook`/`tap` lines (with any leading `--flag value` pairs, e.g. `hook --agent antigravity --event Stop {…}`) through `orch hook` / `orch tap`, and a `draft <flag> [<conversation flag>]` line in its `--script` makes it answer as a one-shot Draft whenever its argv contains `<flag>` (the Claude tests use `draft -p --resume`). With `--input-format stream-json` in its argv it reads the prompt from an agy-style user event, and with `--output-format stream-json` it answers in agy's NDJSON events; a `draft-error <text>` line then makes that result an `ERROR` with `<text>` and a failing exit.
8. **Update this document** and `CONTEXT.md` if the Agent brings a concept the glossary lacks.

## Testing against a real agy

Adapter and Daemon tests never start a real Agent. For Antigravity there is an opt-in suite, `crates/orch/tests/real_agy/`, that drives a signed-in `agy` through the Daemon and Holder in a cached template HOME (onboarded with data sharing off, Agent hookup installed by `orch agent install`), with a cleared environment, so your `~/.gemini` is never touched:

```sh
ORCH_REAL_AGY=1 cargo test -p orch --test real_agy -- --ignored
```

It covers launch with `-i`, agy's workspace-trust screen (shown in the pane while the Session stays Starting), hooks through the hookup, Needs input on a permission prompt, Idle on `fullyIdle`, resume with `--mode`, one Subagent, a Draft (including whether agy's stream-json print mode answers the user event on stdin) and whether agy's OSC 11 query stalls its start in the Holder. Adding `ORCH_REAL_AGY_RECORD=1` re-records the scrubbed fixtures in `crates/orch-agent/tests/fixtures/antigravity/`. Its README lists the prerequisites and what each test checks. Without `ORCH_REAL_AGY=1` the tests are no-ops, and CI never runs them.
